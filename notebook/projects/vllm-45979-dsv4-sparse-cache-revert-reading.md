### The Cache Logic (Detailed)

```
★★★★★★★★★ Understanding what the sparse cache actually caches:

The DSV4 flashinfer attention path has THREE sparse attention modes per layer:
  → SWA-only (compress_ratio=1): sliding window attention, no compression
  → C128A (compress_ratio=128): global attention with 128x compression
  → C4A (compress_ratio=4): global attention with 4x compression

For SWA-only and C128A modes:
  → Both call build_flashinfer_mixed_sparse_indices() with SAME metadata
  → The mixed sparse indices are identical for these two modes
  → Previously: rebuilt for every layer → redundant computation
  → With cache: build once, reuse across layers → 2%~4% TTFT improvement

C4A mode:
  → Uses DIFFERENT metadata (no c128a_global_decode_topk_indices)
  → Cannot share cache with SWA-only/C128A
  → Correctly NOT cached (cache_key == "c4a" → bypass cache)

★★★★★★★★★ KEY DISTINCTION: This cache is PER-REQUEST, PER-STEP:
  → Cache stored in DeepseekSparseSWAMetadata (created per forward pass)
  → Metadata is per-request, per-step → cache is NOT stale across steps!
  → Within a single forward pass, same metadata is shared across layers
  → → Caching across layers within same step is SAFE
  → → This is NOT the same as caching across steps (which would be stale)

★★★★★★★★★ This is fundamentally different from the CUDA graph problem:
  → CUDA graph: captured ONCE → replayed MANY times → stale metadata
  → Sparse cache: computed EACH forward pass → reused within SAME pass → fresh metadata
  → The sparse cache is an intra-step optimization, NOT an inter-step cache!
```
