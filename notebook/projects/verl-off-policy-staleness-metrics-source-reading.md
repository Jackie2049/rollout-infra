## 1. Problem: Async GRPO Staleness

In async training (verl Sleep/Wake, rLLM Async Trainer):
- Rollout and training are decoupled → multiple model versions exist concurrently
- Trajectories generated by older model versions → stale relative to current policy
- Staleness causes: off-policy divergence, IS weight instability, training quality degradation

Previously: NO metrics to quantify staleness → blind training → no way to detect or control it.

---

## 2. New Metrics (PR #6736)

### trajectory_spans

```python
trajectory_spans = max_global_steps - min_global_steps + 1
```

**Meaning**: How many distinct model versions a single trajectory spans.

- `trajectory_spans = 1` → fully on-policy (all tokens from same model version)
- `trajectory_spans > 1` → off-policy (tokens from different model versions)
- Higher spans → more staleness → more divergence

### trajectory_staleness

```python
trajectory_staleness = (global_steps - 1) - max_global_steps  # lower bound
trajectory_staleness_worst = (global_steps - 1) - min_global_steps  # worst case
```

**Meaning**: How many training steps the trajectory lags behind current policy.

- `global_steps` = current training step
- `max_global_steps` = most recent model version used in trajectory
- `min_global_steps` = oldest model version used in trajectory
- Lower bound: trajectory at most `staleness` steps behind
- Worst case: trajectory at most `staleness_worst` steps behind

### Logged metrics

```python
metrics = {
    "training/off_policy/trajectory_spans/mean": ...,
    "training/off_policy/trajectory_spans/max": ...,
    "training/off_policy/trajectory_staleness/mean": ...,
    "training/off_policy/trajectory_staleness_worst/mean": ...,
}
```

These metrics are logged per training step → continuous monitoring of off-policy drift.

## 3. Replay Buffer Staleness Fix

### Before: arbitrary sampling order

```python
selected_prompt_uids = list(finished_keys.union(failure_keys))[:batch_size]
```

Arbitrary order → stale trajectories sampled as often as fresh → staleness accumulates.

### After: prioritize oldest prompts (smallest global_steps)

```python
sampleable_keys = sorted(finished_keys.union(failure_keys),
                         key=lambda key: prompt_global_steps.get(key, 0))
selected_prompt_uids = sampleable_keys[:batch_size]
```

Sorted by global_steps → oldest (most stale) trajectories get sampled first → they exit the buffer sooner → staleness doesn't accumulate!

### Key insight: sampling oldest first REDUCES staleness

- Oldest trajectories = most stale → get processed first → removed from buffer
- Fresh trajectories wait → accumulate less staleness before being processed
- Result: average staleness decreases → more on-policy training

## 5. RTX 4090 Impact

### Async GRPO on RTX 4090

RTX 4090 uses Sleep/Wake mode (verl) or Async Trainer (rLLM Tinker):
- Rollout phase: model on GPU → generate trajectories
- Training phase: model on GPU → update policy
- Time-multiplexing: GPU alternates between rollout and training

With async training:
- Trajectories generated during rollout → model version at global_steps=t
- Training happens later → model now at global_steps=t+N
- Staleness = N steps → off-policy behavior

### How #6736 helps RTX 4090

1. **Monitoring**: trajectory_spans/staleness metrics → detect when staleness is too high
2. **Control**: replay buffer prioritizes oldest → reduce staleness accumulation
3. **Tuning**: set staleness thresholds → abort if trajectory_staleness exceeds limit
4. **Debugging**: if training diverges → check metrics → likely staleness too high

### Recommended RTX 4090 async GRPO configuration

```python
# verl config
staleness_monitor = True  # enable off_policy metrics logging
replay_buffer_priority = "oldest_first"  # prioritize smallest global_steps

# rLLM Tinker config (from our source reading)
async_trainer.enable = True
async_trainer.staleness = 0  # zero staleness tolerance → immediate processing
async_trainer.trigger = 4     # trigger training after 4 trajectory groups
```
