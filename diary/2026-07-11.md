## Entry 3: Deep Analysis — verl #7016 Qwen3-MoE FSDP2 Backward Failure

★★★★★★★★★ BREAKTHROUGH: Found **PyTorch PR #174862** that directly explains the root cause!

### Root Cause: FSDP2 MoE Gradient Graph Divergence
PR #174862 (skpark-rh, Feb-June 2026) addresses "differing gradient computation graphs in different ranks":

1. **MoE Router = Data-Dependent Execution**: Each token's top-K expert selection varies per rank. Forward pass loops over experts, processing only selected tokens → dynamic computation graph
2. **FSDP2 assumes SPMD**: NCCL reduce-scatter expects identical input sizes across ranks. Different experts activated → different gradients → mismatched reduce-scatter input sizes
3. **Gradient checkpointing exacerbates**: Saved-tensor count depends on which experts visited during recomputation → CheckpointError
4. **Without checkpointing**: SIGSEGV when NCCL collective sees mismatched input sizes

### Fix (PR #174862)
```python
self._zero_buf = torch.zeros(max_unused_param_size, ...)
unsharded_grads[idx] = self._zero_buf.expand(param_unsharded_size)
```
Guarded by `reduce_scatter_unused_params` flag. Still OPEN as of June 24 (last commit).

### RTX 4090 Implication
- dp=1 avoids cross-rank divergence (single rank), so Failure B (SIGSEGV) likely won't occur
- **BUT** Failure A (CheckpointError) CAN still occur — it's a local data-dependent saved-tensor issue, not cross-rank
- MUST use FSDP1 with Qwen3-MoE on RTX 4090

### Key Architecture Findings

**Bypass mode**: TRL implements bypass mode IMPLICITLY via `.detach()` when `num_iterations==1` and generation steps are aligned. No explicit flag like verl's `bypass_mode=True`. This means the same forward-pass saving optimization already exists but is undocumented and non-configurable.

**Liger kernel**: Fused GRPO loss bypasses `model.forward()` entirely — calls backbone directly, multiplies by `lm_head.weight`. Incompatible with PEFT on lm_head and prompt-learning methods.

**Reward system**: Multi-reward-function with per-function weighting, async coroutine support via daemon event loop, environment-owned rewards via `get_reward()`.

**Entropy control**: Static coefficient OR adaptive PID-like controller with running window, adjustable up/down per optimizer step.

**8 loss types**: grpo (PPO-clip), bnpo, dr_grpo, dapo, luspo, cispo (one-sided clip), sapo (soft sigmoid), vespo (gamma weights).
