## 10:00 — Triton Decode Attention Kernel 正确性修复验证

### Bug修复与验证

修复了之前Triton decode attention kernel的关键bug:

**根因**: padding positions (kv_positions >= S) 通过mask `other=0.0` 加载为K=0, 产生score=0。在online softmax中, `exp(0 - m_new) ≠ 0` → padding位置贡献非零attention weights → 腐化归一化 → 输出小5-16x。

**修复**:
1. `scores = tl.where(valid_kv, scores, float("-inf"))` → padding score=-inf → exp(-inf)=0
2. `p = tl.where(valid_kv, p, 0.0)` → 零化padding位置的attention weights

**验证结果**:
- Triton vs Naive: cos_sim=**1.000000**, max_diff=0.000732 → 完全正确!
- Triton vs SDPA(is_causal=False): cos_sim=**1.0** → 与正确baseline完全一致
- Triton vs SDPA(is_causal=True): cos_sim≈0.02-0.09 → 但这是SDPA的问题(而非Triton)

### SDPA is_causal=True 对Decode Q=1的Bug

发现一个重要认知: **SDPA `is_causal=True` 对decode (Q=1) 产生错误结果!**

- SDPA将Q视为position 0 → causal mask限制Q只能看K[0] → 只attention到1个position
- 但decode场景中Q应该是在position S → 可以看到所有K positions[0..S-1]
- 这解释了为什么FA2 decode在RTX 4090上3-34x更慢(加上layout转换开销) + 结果错误
- 正确做法: decode使用 `is_causal=False` 或专用decode kernel

## 14:00 — TransformerEngine (NVIDIA) FP8 Deep Read

### 源码深读

深入阅读NVIDIA TransformerEngine源码, 重点理解FP8量化机制:

**5种Scaling Recipes**:
1. **DelayedScaling**: 经典方法, scale=FP8_MAX/amax/(2^margin), 使用上一步的amax → 1步delay
2. **Float8CurrentScaling**: 无delay, 直接扫描当前tensor amax → 更精确
3. **MXFP8BlockScaling**: 32-value blocks, E8M0 power-of-2 scales (需Blackwell)
4. **Float8BlockScaling**: FP32 block scales (需Hopper+CUDA 12.9)
5. **NVFP4BlockScaling**: 2-level quantization (需Blackwell)

**RTX 4090限制**: SM89只能用DelayedScaling和Float8CurrentScaling

**FP8 Linear Forward流程**:
1. quantize input → tex.quantize() C++ kernel
2. quantize weight → quantize_weight()
3. FP8 GEMM → general_gemm() (fused quantize+GEMM+dequantize)
4. output → dequantize to BF16/FP32

**rowwise+columnwise双量化**: QuantizedTensorStorage同时存rowwise和columnwise量化数据 → backward无需重新量化

**关键对比**: 我们之前Python-level FP8 dequant慢1.5-2.5x → TE用fused C++ kernel避免此overhead

## 23:30 — TE GEMM cuBLASLt Dispatch Deep Dive

### 源码追踪: Python → C++ → cuBLASLt 完整5层调用栈

追踪了TransformerEngine FP8 GEMM的完整dispatch chain:

```
Python general_gemm() → tex.generic_gemm() → C++ gemm() → nvte_cublas_gemm_v2() → cublas_gemm() → cublasLtMatmul()
```

### 核心发现

**1. CanonicalizeGemmInput: RTX 4090强制TN layout**
- `nvte_is_non_tn_fp8_gemm_supported()` 在SM89返回0 → RTX 4090只支持TN的FP8 GEMM
- TE自动转换: A不transposed → 用columnwise数据(转置版) → 强制TN
- B transposed → 用columnwise数据(转置版) → 强制TN
- Blackwell(SM100)返回1 → 支持任意layout

**2. FP8 Scaling Mode Dispatch**
- RTX 4090(Delayed/Current): `CUBLASLT_MATMUL_MATRIX_SCALE_SCALAR_32F` → 每tensor一个FP32 scale
- MXFP8: `VEC32_UE8M0` → 需SM100+(RTX 4090❌)
- NVFP4: `VEC16_UE4M3` → 需SM100+(RTX 4090❌)
- Block: `VEC128_32F` → 需CUDA 12.9+(RTX 4090 CUDA 12.8❌)

**3. FP8 Dequant在cuBLASLt内部自动完成**
- `A_SCALE_POINTER` + `B_SCALE_POINTER` → cuBLASLt内部: FP8×scale_inv → 自动反量化
- 输出直接BF16 → **无需Python量化/反量化!** → TE比Python FP8快1.48-1.59x的根因!

**4. Fused vs Unfused Quantization**
- DelayedScaling + Float8Tensor → **Fused** → cuBLASLt内置处理 → 1个kernel
- CurrentScaling + Float8Tensor → **Fused** → 同上
- 其他recipe → **Unfused** → GEMM→BF16→再量化 → 额外开销

**5. FAST_ACCUM / Split Accumulator**
- `use_split_accumulator=true` → FP32累加器 → 精确但稍慢
- `use_split_accumulator=false+FP8` → fast accumulation → 低精度但快

**6. Epilogue Fusion**
- `CUBLASLT_EPILOGUE_BIAS`: D = AB + bias
- `CUBLASLT_EPILOGUE_GELU_AUX_BIAS`: D = GELU(AB + bias)
- `CUBLASLT_EPILOGUE_BGRADB`: D = AB, dbias = sum(dy)
- RTX 4090支持所有epilogue fusion!

**7. Workspace: 4MB(SM89) vs 32MB+1024B(SM≥9)**

## 24:30 — CUDA Kernel Optimization Patterns SM89 Deep Dive

创建SM89(RTX 4090)专用的CUDA kernel优化模式笔记, 9节内容:

**核心内容**:
1. **SM89 vs SM90对比**: SM89=warp-centric(32线程)+cp.async+HMMA, SM90=warp-group-centric(128线程)+TMA+WGMMA
2. **cp.async Pipeline**: SM89核心优化! 3-stage software pipeline → 20-30% vs手动加载
3. **HMMA指令**: 16×8×16形状, FP16/BF16/FP8/INT8; FP8 E4M3在SM89支持; SCALAR_32F per-tensor scaling
4. **ldmatrix**: 矩阵数据加载指令 → 自动避免bank conflict + 布局转换
5. **Memory Coalescing**: 连续访问=100%效率, stride-32=3.1%效率; FP8=1B→带宽省50%
6. **smem 100KB约束**: 3-stage FP16=96KB→1 block/SM; FP8=48KB→2 blocks/SM→2×occupancy!
7. **Register Budget**: HMMA kernel需要~40 regs/thread → 83% occupancy; >64→50% occupancy
8. **FP8 HMMA数据流**: BF16→FP8(E4M3)→HMMA→FP32累加×scale_inv→BF16输出
9. **SM89设计决策树**: compute-bound→2-stage; memory-bound→3-stage; 极端memory-bound→4-stage(occupancy风险)

**关键洞察**: SM89与SM90的kernel设计策略完全不同
- SM89瓶颈=数据搬运(无TMA) → cp.async pipeline是核心
- SM90瓶颈=调度(多WG协调) → TMA自动搬运, 重点关注WGMMA调度
- FP8在SM89的smem优势: 50%空间省→occupancy翻倍→额外性能提升!

## 62:00 — torch.compile Benchmark (RTX 4090 实测!)

### 核心发现: torch.compile只在B=1有效, B>=4反而更慢!

**Forward Pass实测**:

|-------|-----|-----|------|------|
| 7M | **4.09x** | 0.80x ❌ | 0.85x ❌ | 0.88x ❌ |
| 25M | **3.00x** | 0.90x ❌ | 1.04x | 0.97x ❌ |
| 7B-proxy | 1.16x | 0.95x ❌ | 0.97x ❌ | - |

**Training Step实测**:

| Model | B=4 | B=16 | B=32 |
|-------|-----|------|------|
| 7M | **1.96x** | 1.19x | 1.05x |
| 25M | **1.65x** | 1.03x | 1.01x |

**Compile Modes (7M B=16)**:
- default: 1.07x (最佳)
- reduce-overhead: 1.02x
- max-autotune: 0.92x (最差! Triton GEMM慢于cuBLAS)

**Dynamic Shapes**: 全部0.88-0.98x → 更慢!

**Memory**: Eager 562MB vs Compiled 555MB → -1.2% (编译节省内存)

### 关键分析

**为什么B=1加速4x**: Python overhead消除(eager 1.2ms中~0.9ms是overhead → compile消除后仅0.3ms)

**为什么B>=4反而慢**: torch.compile用Triton GEMM → Triton GEMM比cuBLAS慢1.5x → 大batch时GEMM主导 → 整体更慢

**为什么max-autotune最差**: autotune选择Triton kernel → Triton GEMM慢于cuBLAS fallback → default mode用cuBLAS反而更好!

**结论**:
- 推理(B>=4): torch.compile无用甚至有害 → 用FlashInfer(15.72x)代替
- 训练(B<=4): 1.65-1.96x加速 → 有价值(消除backward Python overhead)
- 训练(B>=16): 1.01-1.05x → 几乎无收益
- 推荐mode: default → cuBLAS fallback更稳定
